# DBVORA P0-13 — SQLite ASCII-only FK-index audit correctness (2026-11-11 KST)

## Defect and consequence
`dbvora/schema_review.py::_covered` compared foreign-key column references to covering index column names and declared PK column names using exact Python string equality. SQLite identifier lookup compares ASCII A-Z without case. If metadata surfaces distinct ASCII case, an existing covering index can be labeled `FK_INDEX_REVIEW`; the advisory was a false positive. Unicode case folding is not allowed.

## Designs compared
- A (selected): reuse `dbvora.sqlite_identifiers.sqlite_identifier_key` in bounded, metadata-only column prefix checks. No new dependency/network/SQL access, low cost, narrow regression surface, preserved offline schema report.
- B (deferred): reopen each DB and interrogate PRAGMA for every edge to normalize at read time. More DB I/O, changes read-only connection lifetime and UI latency and requires broader Windows/WAL races/integration QA. Not justified for a casing-only bug.

## Change and invariants
- Indexes: only full, non-partial leading-column prefixes count; expression-index `None` does not count. Invalid column values reject as `INVALID_WORKSPACE`.
- PK: declared PK prefix uses SQLite ASCII-only identifier comparison; no conversion of executable SQL.
- No table row reads, credentials, network access, customer data or source archive writes; no cross-DB relationship inference.
