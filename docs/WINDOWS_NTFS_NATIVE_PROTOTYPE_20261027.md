# DBVORA — Experimental native Windows NTFS create-only publication (2026-10-27 KST)

## Approved decision and scope
The owner explicitly approved exploring **Option B: a Windows NTFS-specific safe publication backend**. The existing `dbvora/archive/safe_zip.py` and its fail-closed directory fsync behavior are preserved. This is a *separately invoked OS-temp synthetic experiment*, not a shipping archive backend or authorization to operate on customer databases.

Official Windows references:
- Microsoft `MoveFileExW`: https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw . `MOVEFILE_WRITE_THROUGH=0x8`; **no** `MOVEFILE_REPLACE_EXISTING`, `COPY_ALLOWED`, or `DELAY_UNTIL_REBOOT`. The documented flush guarantee specifically discusses move-by-copy-and-delete and is not proof that every rename metadata update survives sudden power loss.
- Microsoft `FlushFileBuffers`: https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers . Requires a writable file handle. The staging file is opened `r+b` for file `os.fsync`; source/customer files are never opened.
- Microsoft `Directory Handles`: https://learn.microsoft.com/en-us/windows/win32/fileio/obtaining-a-handle-to-a-directory . A directory handle is possible with `FILE_FLAG_BACKUP_SEMANTICS`, but the documented permitted operations do **not** independently establish directory metadata flush/physical durability.

## Implemented files
- `dbvora/archive/windows_ntfs_publish.py`: check local OS-temp directory, strict generated stage/target names, regular-file/no-symlink staging, file identity, create-only Win32 `MoveFileExW`, post-move SHA-256 + size equality. No overwrite/copy flags. Returns stable sanitized error codes.
- `scripts/windows_ntfs_publish_probe.py`: explicit `--synthetic-only` CLI, Windows/Python3.11/NTFS OS-temp checks before any file writes. Creates generated bytes only, exercises new-name move + SHA, existing-target preservation, injected failure preserving staging. The work is inside `TemporaryDirectory` and never accepts a file path argument. Returns `PASS_WINDOWS_NTFS_SYNTHETIC_ONLY` if run natively, or `BLOCKED_UNVERIFIED` otherwise; mock-injected success is labeled `PASS_SIMULATED_ONLY`. **Even native synthetic success still reports** `ready_for_customer_data=false`, `power_loss_durable_verified=false`, `directory_metadata_durable_verified=false`.
- `tests/test_windows_ntfs_publish.py`: 12 synthetic boundary/failure tests, including zero-overwrite collision, injected failure, changed bytes detection, stage symlink rejection, unsafe path, non-NTFS, wrong Python version, mocked/non-native certification, flag safety and writable stage handle.

**Unchanged:** production `safe_zip.py`, customer archive CLI, receipts, retention and any real backup outputs. No user/customer data, credentials, network services, paid CI, repo promotion or public deploy.

## Remaining safety gates before integration or commercialization
1. Independently verify Windows native file-handle flush and create-only move API behavior on NTFS, failure injection and collision. Run Python regression without unexpected skips.
2. Establish actual namespace durability guarantees or a documented fail-closed/recovery design. `MOVEFILE_WRITE_THROUGH` returning success alone does **not** prove full sudden-power-loss persistence.
3. Only after native proof, design a separate opt-in adapter for actual archived SQLite snapshots, perform exact content restore+WAL+receipt audits, force-failure and concurrency tests. No original/verified backup overwritten.
4. Real `file://` browser, Windows installer, machine/process termination, independent backup recovery, physical power interruption and customer consent remain separate checks. Do not promote main/develop or claim customer readiness before them.
