# DBVORA P1-PG01 — Opt-in PostgreSQL metadata-only connector

**2026-11-11 KST** · `hibi89/DBVORA@feature/p0-db-map`. Prototype only. No actual PostgreSQL credentials, server or row data accessed during development.

## Scope and alternatives
- **A (selected):** optional `psycopg 3` session in a separate, metadata-only connector. User must intentionally provide a DSN. The connector enforces `sslmode=verify-full`, a 5-second connect timeout, a read-only transaction and bounded query time. Uses constant SQL catalog queries with positional parameters; only schemas/tables, attributes, indexes and declared FK relations. No ORM, schema names never interpolated.
- **B (deferred):** general SQLAlchemy multi-engine adapter to support many DBs at once. More dependencies/driver surprises, higher testing burden and a larger risk that a generic query API would read data rows. Defer until actual PostgreSQL behavior and ACLs are proven.

## Implemented
- New `dbvora/connectors/postgres_reader.py`: `inspect_catalog(read_only_connection)` for testable metadata-only inspection. Query-only `pg_catalog.pg_class`, `pg_namespace`, `pg_attribute`, `pg_constraint`, `pg_index`. Bound 300 tables, 300 columns/indexes/FKs per table, fail-closed on invalid metadata and foreign-key targets outside visible inventory.
- `inspect_postgres(dsn)` imports optional psycopg lazily and opens a user-initiated, TLS-verified read-only session; errors report constant safe codes, not DSNs. No automatic discovery or cloud exchange. This API is not wired to the current SQLite-only workspace or installed customer UI.
- Metrics reflect `pg_total_relation_size` if returned by a future server; no invented per-database CPU/RAM or historical growth rates. A metadata-only connection property does **not** itself prove that the underlying database role lacks writes.
