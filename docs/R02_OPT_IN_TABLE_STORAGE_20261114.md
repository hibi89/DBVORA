# R02 opt-in SQLite dbstat page measurement — 2026-11-14 KST

## User goal and architecture decision
- User-final R02: visually inspect measured DB/table capacity with clear scope and provenance, never fabricate unavailable CPU/RAM or row sizes.
- A: automatically scan dbstat for every table at initial refresh. Benefit: instant data. Downsides: up to 1,000 tables, extra latency for every page load, potentially misleading all-table scan overhead.
- B: place an explicit button in the selected table inspector; invoke a new same-origin GET endpoint once per click, reuse existing read-only `collect_table_storage` which caps main file size at 64MiB and scan time at 0.75s. Unavailable is displayed as unavailable. **Selected B**, no cloud, no SQL from user parameters, no new dependencies, no eager DB scan.
- `GET /api/table-storage?table=<URI-encoded selected name>` validates a single bounded name present in fresh `inspect_sqlite`; reads only metadata, returns `dbvora.local-table-storage.v1` with explicit `metric.status`, `metric.allocated_btree_bytes` (if measured) and documented `dbstat` scope. Inherited loopback Host/Origin/method guards apply. Checks source file identity before and after bounded scan to reject main-file replacement.
- UI `dbvora/web/app.js` renders an on-demand measurement button, explains allocated B-tree pages (including indexes) are **not** exact physical disk size or row bytes, has disabled while working, 8s abort and clear measured/unavailable/error states. Filter/selection/resize observer and existing P0 viewer unchanged.
